## Headline

**85 % of the placed world meshes are drawn at the wrong size, and 25 % with the wrong handedness.**
- The cause is the export of `StaticMeshCollectionActor` (SMCA) members:
  - it uses only the serialized per-component `CachedParentToWorld` matrix;
  - it drops the component `Scale × Scale3D`, which the engine multiplies on top.
- In Streets, that matrix is always a pure rotation plus translation. **All per-instance scale and mirroring lives only in the component.**
- The same matrices feed `collision*.glb` and `physics.json`, so **collision is wrong in the same way.**

## 1. Component world transform rule

| field | value |
|---|---|
| **Original** | `UPrimitiveComponent::SetTransformedToWorld` **0x82DC3508** (shared by ~40 primitive-component vtables); setters `execSetTranslation` 0x82C50298 → 0x82DC38B0, `execSetScale` 0x82C503C8 → 0x82DC3978, `execSetScale3D` 0x82C50468 → 0x82DC3990 (natives table 0x8370E360..) |
| **Fields** | PrimitiveComponent `LocalToWorld` +0x50 (FMatrix); **`CachedParentToWorld` +0x120**; `Translation` +0x160; `Rotation` +0x16C; `Scale` +0x178; `Scale3D` +0x17C..+0x184; flag dword +0xF4: **AbsoluteTranslation 0x400000** (zeroes the parent translation), **AbsoluteRotation 0x200000** / **AbsoluteScale 0x100000** (re-orthonormalize / strip parent scale; 0x82DC3508 body) |
| **Recovered rule** | `LocalToWorld = ParentToWorld`, with the Absolute* adjustments; then `LocalToWorld = FScaleRotationTranslationMatrix(Scale·Scale3D, Rotation, Translation) (0x82DA62D8) × LocalToWorld` (VMX multiply follows) |
| **Confidence** | **CONFIRMED** that Scale·Scale3D, Rotation and Translation are always applied. HIGH for the multiply order (relative × parent): the VMX tail is not decoded, but this is stock UE3 and consistent with the data |
| **Streets data** | No component has an Absolute* flag. SMCA members have default Translation and Rotation and non-default Scale3D on 1,672 of them. Only `TnForcedDirVolume` (4) has a component Rotation. |
| **Rebuild today** | `vs_map.py` SMCA branch: `M = native matrix` (component transform ignored). The StaticMeshActor / InterpActor branch correctly uses `component_matrix(cd) @ actor_matrix(d)`. |
| **Visible discrepancy?** | **YES — primary cause** of the "incomplete / incorrect geometry" report |

**Correct SMCA member matrix (UE row-vector):**

```
M_world = diag(Scale·Scale3D) · R(Rotation) · T(Translation) · CachedParentToWorld
```

For Streets this reduces to `diag(Scale·Scale3D) · CachedParentToWorld`. The per-component values are in **`notes/data/streets_smca_component_scale.json`** (1,906 entries keyed by component object path; generated by `tools/streets_smca_scale.py` from the cooked packages).

### Actor transform (verified unchanged)
- `ue_actor_matrix` = T(−PrePivot) · S(DrawScale·DrawScale3D) · R · T(Location).
- `ue_rot` = UE3 FRotationMatrix.
- Both match UE3 (**HIGH**, stock; the formula was checked against the FRotationMatrix layout).

### Mirroring
- With the scale applied, 482 members get det < 0.
- The Rebuild glTF loaders already swap winding for det < 0 (`Gltf.cpp:221–229`). UE3 does the same via LocalToWorldDeterminant / reverse culling (HIGH, stock).
- Normals: the loaders transform by the world 3×3 and normalize. That matches UE3 LocalVertexFactory (L2W 3×3, then normalize). No change needed (HIGH).

## 3. BSP

**HIGH: no discrepancy found.**
- BSP exists only in ART: Model_9419, 889 nodes, 427 surfaces, 2,460 triangles. BASE has an empty Model.
- Every polygon node is covered by exactly one cooked FModelElement (AssetTools audit).
- Winding: `vs_map` orients each fan triangle to the surface `vNormal`. UE3 BSP is single-sided unless PF_TwoSided, front = normal side. Model points are world-space, so no transform applies.
- UVs: `((P − Points[pBase]) · TextureU, ·TextureV) / 128`, as in the UE3 model vertex buffer.
- Materials: 65 nodes on 47 brushes resolve to `EngineMaterials.DefaultMaterial`. They are rendered and collidable, so if any is visible in the rebuild it would appear as the engine default material, as in UE3.
  - **PARTIAL:** whether these faces are covered by meshes in the original. They are usually hidden behind the corrected-scale meshes. Re-check after fix §1.
- PolyFlags: the census is 314 × 0x0, 112 × **0xE00**, 1 × 0x800.
  - AssetTools labels 0x200 / 0x400 / 0x800 with UE2 names (Cutout / FakeBackdrop / Mirror). In UE3 these bits are not those render modes.
  - No code in any lane acts on the labels, so there is no visible effect. **AssetTools labelling correction.**

## Particle size × component/actor scale (native, 2026-10-04, rendering request)
CONFIRMED in the xex (Ghidra headless, read-only).
- **Vtables:** sprite instance vtable 0x8233A9E8 (GetType 0x83071C10); mesh instance vtable 0x82337CA0 (GetType 0x83067830).
- **Sprite FillReplayData** (slot 8, 0x8300C678): ReplayData.Scale (+0x24..0x2C) = 1 × Comp.Scale(+0x178) × Comp.Scale3D(+0x17C..0x184); then, if Owner (+0x34) is set and AbsoluteScale (+0xF4 & 0x100000) is clear, × Owner.DrawScale(+0x140) × DrawScale3D(+0x144..0x14C). There are no other gates.
- **Mesh FillReplayData** (slot 8, 0x83052BD8): the same product, with two gates (bit names HIGH confidence):
  - the whole block is skipped when RequiredModule +0x38 bit31 is set (bUseLocalSpace);
  - the component part is skipped when instance+0x154 & 0x40000000 is set (ignore component scale).
- **Tick:** slot 17 (0x83012DB0 sprite/base, 0x8300D268 mesh) computes the same product for bounds.
- **DrawScale offsets:** execSetDrawScale 0x82C48050 → 0x82E4DC98 writes +0x140; execSetDrawScale3D 0x82C480F0 → 0x82E4DCD8 writes +0x144..0x14C.
- **Not traced:** the render-side vertex fill (Size × Scale); HIGH confidence it matches stock UE3.
- **Owner:** Rendering.
